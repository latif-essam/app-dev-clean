# Cleanup and package-recovery review

Reviewed 2026-09-15 at `57aa87d`, including the local terminal-output fix.
This report proposes changes; it does not implement new cleanup behavior.

The next release should make cleanup narrower and recovery more predictable. Preserve lockfiles and downloaded package caches, diagnose the problem, and choose the smallest useful repair. The existing detector/target structure is small enough to support this without a rewrite.

## Preserve useful dependency data

The current `js` target removes both `node_modules` and `package-lock.json`; the iOS target removes both `Pods` and `Podfile.lock`. These are intentional current behaviors, but lockfiles are valuable project inputs, not disposable caches. A subsequent install can resolve a different dependency tree after they are removed. Keep lockfiles in ordinary clean/reinstall workflows and make dependency upgrades a separate explicit operation. CocoaPods documents that `pod install` retains versions from `Podfile.lock`. [CocoaPods lockfile behavior](https://guides.cocoapods.org/using/pod-install-vs-update.html).

The tool always uses `npm install` and `pod install --repo-update` (`internal/detectors/rn.go:83`). Add a package-manager adapter that checks the project's declared manager/version, lockfiles, and workspace configuration. Stop on conflicting lockfiles rather than choosing arbitrarily. Preserve project registry and install settings; detect Bundler when a project uses it. Refresh CocoaPods repository metadata only when requested or needed for a diagnosed resolution error. [CocoaPods command reference](https://guides.cocoapods.org/terminal/commands.html).

There are two different things to preserve: an installed dependency tree and the downloaded archives used to rebuild it. The existing JS target leaves npm's download cache alone, which is useful. The larger global targets erase complete shared stores and can make subsequent work download packages again.

| Ecosystem | Suggested approach | Limitation |
|---|---|---|
| npm | Diagnose missing/invalid dependencies first. Use a targeted `npm rebuild <package>` for a native-build problem when appropriate. Retain the download cache. For an explicitly requested complete reinstall with a consistent lockfile, use `npm ci --prefer-offline`. | `npm ci` removes the entire installed tree; it belongs in full reinstall, not minimal repair. Cache preference still permits fetching missing data. Install scripts may make their own network requests. |
| pnpm | Respect the pinned manager; use `pnpm install --frozen-lockfile --prefer-offline` when reinstalling. Inspect the store with manager commands. Offer store pruning separately. | Pruning can remove packages needed again after a branch switch, causing later downloads. |
| Yarn | Detect Classic versus modern Yarn and the node_modules/PnP layout. Use the matching lockfile-preserving install mode and retain its cache. | Modern `--check-cache` refetches packages; it should not be the default bandwidth-saving check. |
| CocoaPods | Retain `Podfile.lock` and the shared download cache; try the project's normal `pod install` path before deleting all Pods. | A missing archive or changed dependency still requires a download. |
| Gradle | Separate generated build outputs from downloaded dependencies. Prefer Gradle's cache handling; offer offline or dependency-refresh actions for specific diagnoses. | `--offline` fails if required dependencies are absent. Refresh checks remote metadata and may fetch changed artifacts. |

Sources: [npm clean install](https://docs.npmjs.com/cli/commands/npm-ci/), [npm cache preference](https://docs.npmjs.com/cli/v8/using-npm/config/#prefer-offline), [npm targeted rebuild](https://docs.npmjs.com/cli/v11/commands/npm-rebuild/), [pnpm install](https://pnpm.io/cli/install), [pnpm store](https://pnpm.io/cli/store), [Yarn install](https://yarnpkg.com/cli/install), [Gradle dependency caching](https://docs.gradle.org/current/userguide/dependency_caching.html).

`npm cache verify` validates cached data and performs garbage collection. It does not prove that all installed files in `node_modules` are healthy. Package caches also are not durable backups of personal files. [npm cache documentation](https://docs.npmjs.com/cli/v11/commands/npm-cache/).

## Proposed user flows

These names are proposals, not commands available in the current release.

| Flow | Purpose | What it preserves |
|---|---|---|
| Doctor | Inspect root, manager/version, lockfile consistency, installed dependencies, and relevant failure logs; recommend a targeted action. | Project files and dependencies; network checks are explicitly identified. |
| Clean build outputs | Remove selected generated outputs or project-owned bundler caches. | Installed packages, lockfiles, downloaded archives. |
| Repair dependencies | Use the package manager's appropriate targeted repair or rebuild after diagnosis. | Unrelated packages and lockfiles where the manager supports this. |
| Reinstall dependencies | Recreate a selected project's dependency tree from its lockfile, preferring cached archives. | Lockfiles and shared caches. |
| Reclaim shared cache space | Separately review unused or old cache entries and reclaim space with manager-supported operations. | Active data where the manager can establish ownership; explain future download cost. |

Show the action plan before execution: exact resolved paths, ownership/scope, estimated bytes, lockfiles being preserved, commands to run, and whether downloads may be needed. Report estimates as estimates; dry-run should say “would reclaim,” not “reclaimed.” A transaction log with outcomes helps diagnosis and retry. Optional move-aside recovery can preserve a dependency directory during repair when disk space allows, but it does not free space until the old copy is removed.

For shared caches, respect configured locations such as `GRADLE_USER_HOME` and `PUB_CACHE`; the current platform resolver hardcodes defaults. Reject empty or relative cache roots. Avoid manipulating active stores behind a package manager's locking scheme.

## Sharing package downloads between devices

Existing local caches are the first improvement. For multiple machines or CI, an optional registry proxy such as Verdaccio can cache requested npm-compatible package archives and share them across clients. This is a separate infrastructure feature, with storage, access control, and maintenance costs. It can reduce repeated upstream downloads but still needs initial cache population. Share package archives through supported cache/registry mechanisms; installed native binaries can depend on the destination OS and architecture. [Verdaccio caching](https://www.verdaccio.org/docs/caching/).

Do local diagnosis first. Contact the configured registry for missing or suspect pinned artifacts when needed. Checking every dependency remotely on every clean can itself waste bandwidth. Do not promise a download-saving percentage without measurements.

## Installing on another device

The repository's documented Homebrew path for macOS/Linux is:

```sh
brew install latif-essam/tap/app-dev-clean
app-dev-clean --version
```

With Scoop already installed on Windows:

```powershell
scoop bucket add latif-essam https://github.com/latif-essam/scoop-bucket
scoop install app-dev-clean
app-dev-clean --version
```

Run the tool inside a supported project. The release configuration builds macOS, Linux, and Windows for amd64 and arm64. These commands install the published package, not uncommitted local changes. The previous project notes record a successful Mac Homebrew install; the Windows Scoop path still needs real-device verification. Direct install scripts should also verify the release checksums and clean up temporary downloads.
